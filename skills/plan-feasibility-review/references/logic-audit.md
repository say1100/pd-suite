# 逻辑审计方法

第 1 步(逻辑审计)的详细操作手册。按顺序执行四个检查,输出到报告的"逻辑审计"节。

## 1. 假设提取与排序

计划书里的风险几乎都写在字缝里。逐段读计划,对每个"默认成立"的前提打标。常见隐含假设清单:

- **需求侧**:用户真的有这个问题吗?有问题的用户真的会付费/换习惯吗?现有替代品(包括"什么都不做")真的差吗?
- **技术侧**:指标目标(精度/延迟/成本)是工程可达的吗?当前 demo 指标是在什么条件下取得的?
- **成本侧**:单位经济模型成立吗?成本曲线假设(摩尔定律式下降)有依据吗?
- **渠道侧**:触达用户的路径存在吗?获客成本估过吗?
- **合规侧**:监管、资质、数据合规允许吗?周期估了吗(医疗、金融常以年计)?
- **竞争侧**:大厂为什么没做/做不赢?壁垒是什么、能维持多久?

**排序公式:关键性 × 不确定性。**
- 关键性:这个假设塌了,项目死不死?(死 → 关键)
- 不确定性:现在有直接证据吗?(没有 → 高不确定)
- **关键假设 = 高关键性 + 高不确定性**。只对关键假设安排验证实验;非关键假设记录在案即可。

## 2. 因果链检查

把计划压缩成六跳链条,逐跳问"凭什么":

```
问题存在 → 有人需要解决 → 本方案能解决 → 方案能交付出来 → 用户会采用 → 采用能变现
```

每一跳的合格证据标准不同:
- 问题存在:用户访谈、行为数据、公开痛点记录——不是"我认为大家都有这个困扰"。
- 需要解决:用户当前在用什么替代?付费意愿的任何真实信号。
- 方案能解决:demo 数据、原型结果、可查的文献/工程上限。
- 能交付:团队能力、供应链、关键部件可得性。
- 会采用:切换成本、习惯证据、渠道。
- 能变现:单位经济、对标公司的真实毛利结构。

**断点判定**:某一跳只有断言没有证据,就标记为因果链断点。断点落在哪一跳,决定项目处于什么验证阶段——这直接影响"下一步"建议(断在"会采用"就该先做获客实验,而不是继续打磨技术)。

## 3. 可证伪性检查

不可证伪的表述 = 无法安排验证 = 危险信号。识别这些模式:

- 度量缺失:"显著提升用户体验""大幅降低成本"——提升多少?从多少降到多少?
- 全称 Quantifier:"所有用户都需要"" inevitably 行业会转向"。
- 事后归因预留:"成了是因为战略,败了是因为执行"。
- 动词模糊:"赋能""打通""深耕"。

处理方式:引用原文,改写成可证伪版本("提升体验" → "7 日留存从 X% 到 Y%"),并指出作者需要补的度量。

## 4. Pre-mortem

想象一年后项目死了,写讣告。操作化步骤:

1. 列出 5–8 个候选死因(覆盖:需求误判、技术不可达、成本失控、合规卡死、竞争碾压、团队散伙、资金断裂、时机错过)。
2. 按"概率 × 死得有多早"选 TOP3。
3. 每个死因配一个**可观察的早期预警信号**(出现什么现象说明正在走向这个死因),预警信号将并入报告的 Kill criteria。

## 常见谬误速查

评审时对号入座,命中就在报告里点名:

- **套娃市场**:TAM 用"行业总规模 × 预估渗透率 1%"。
- **幸存者偏差**:引用成功案例不引用基础比率。
- **沉没成本论证**:"已经投入 X 个月所以继续"。
- **单点依赖**:唯一供应商/唯一渠道/唯一大客户,无备份。
- **技术乐观主义外推**:把"实验室最好成绩"当成"量产平均成绩"。
- **需求错位**:决策者(买单的人)≠ 使用者(有痛点的人)时,只论证了使用者的痛点。
