# Demo 可验证性判定方法

第 2 步(落地审计)的操作手册。回答一个问题:**这个 demo 能否低成本地证明(或证伪)计划的核心假设?**

## 1. 先定位 demo 的证明对象

Demo 最多能证明两件事之一,通常两件都证明不了:
- **技术可行性**:这件事物理上/工程上做得出来。
- **核心价值假设**:目标用户在乎这件事,且在乎到愿意付钱/换习惯。

Demo **不能**证明商业可行性(单位经济、渠道、规模化)。评审时如果计划书拿 demo 当商业成功的证据,直接标红旗。

先写出"这个 demo 声称证明了什么"(主张),后面的判定都针对这个主张。

## 2. 可验证性四条件

一个主张**可验证**,当且仅当四个条件全部满足,缺一标注为不可验证并指出缺什么:

1. **有量化指标**:准确率、延迟、留存、转化率——有数字,不是"效果很好"。
2. **有测量环境**:在什么数据集/什么用户/什么设备上测,环境可复现。
3. **有基线或对照**:跟什么比?没有基线的指标没有意义(92% 准确率是好是坏取决于基线)。
4. **有预算内的时间和成本**:验证费用和时间在项目资源范围内。

## 3. Demo 陷阱排查(逐项检查,命中的标红旗)

- **硬编码/过拟合**:demo 只在作者自己的数据上成立。检查:换一批数据还行吗?代码里有没有针对测试用例的特殊分支?
- **游乐场条件**:理想光照、理想输入长度、静止目标、母语用户……真实使用环境更恶劣。列出 demo 隐含的全部理想化前提。
- **演示者偏倚**:操作者是作者本人,知道"正确用法";新用户第一次上手能复现吗?
- **挑案例**:展示的是最好样本。要求看最差样本或全量分布(最差 10% 的表现)。
- **无基线对比**:"我们的新方法好"——比什么好?多少?
- **"能跑"≠"可用"**:没有错误处理、并发、边界条件、异常输入的 demo 证明的是"概念成立",不是"产品能交付"。
- **单点外推**:一个场景/一个客户/一类组织的成功,直接外推到整个市场。

## 4. 主张 → 最便宜实验映射

对每个关键主张,设计满足下表的验证实验。原则:**用最小的实验先杀掉最大的风险**,顺序按"风险大小 ÷ 验证成本"排。

| 字段 | 要求 |
|---|---|
| 测什么指标 | 一个主指标,可量化 |
| 在哪测 | 环境/数据/人群,可复现 |
| 样本量 | 最小有统计意义的量(比如 30 例或 1 周 real traffic) |
| Pass / Fail | 事先写死的数值阈值,不允许"效果不错" |
| 成本与周期 | 钱 + 时间 |

**验收标准写法示例**:
- ❌ "用户体验有提升"
- ✅ "10 名目标用户中 ≥6 人独立完成核心任务且 SUS ≥ 70;不达标即停止"
- ❌ "识别效果不错"
- ✅ "在 200 例留出集上 F1 ≥ 0.85,最差类别 F1 ≥ 0.75"

## 5. Demo → 产品 Gap 清单

在报告"下一步"之前过一遍,凡是计划书没提的 gap 标出来:
- **数据/规模**:demo 用 10 条样本,产品要 10⁴ 条,采集与标注成本谁管?
- **边界与异常**:错误输入、极端值、对抗输入的行为定义了吗?
- **性能与成本**:demo 单次 3 秒,产品要求多少?规模化后的单位成本?
- **安全与合规**:数据隐私、行业准入、责任划分(医疗/金融尤其)。
- **维护**:模型/规则多久迭代一次,谁来做?

## 6. Kill criteria(写死在报告里)

和用户一起提前定义"停止信号",格式:
- 若 <实验> 在 <期限> 内未达到 <阈值>,则 <停止/转向/降级为研究项目>。
- 至少一条 kill criteria 必须针对**需求侧**(用户不要),而不只是技术侧(做不出来)——最常见的死法是技术做出来了、没人要。
