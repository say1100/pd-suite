# 产品计划可行性评审

目标:对一个产品计划、技术方案或 demo 做出**证据可回溯**的可行性判断,并给出"最便宜的下一步验证实验"。评审分两个视角:**逻辑审计**(计划本身在逻辑上是否成立)和**落地审计**(demo/验证路径能否低成本证伪核心假设)。

## 核心原则

1. **结论先行**:第一行给 GO / 有条件 GO / PIVOT / NO-GO + 置信度(1–10),再给论证。用户要的第一个信息是判断,不是分析过程。
2. **事实、假设、观点分离**:计划的陈述逐条标注 `[事实]`(可查证)、`[假设]`(未验证)、`[观点]`(主观)。可行性风险几乎全部藏在未验证的假设里。
3. **每条结论挂证据**:引用计划原文、可查证数据、或明确写出推理链。信息不足时输出"信息缺口清单",禁止用猜测补位。
4. **反讨好**:评审的价值在发现致命问题。发现致命缺陷必须直说;亮点也要指出,但不得为照顾情绪弱化判断。
5. **外部视角校准**:先估同类项目的基础比率(base rate),再讨论个体差异。对"我们这次不一样"保持警惕——它必须转化为可验证的具体主张才算数。

## 工作流程

### 第 0 步:确认评审对象与材料
- 识别用户给了什么:完整计划书 / 一段想法描述 / 代码或 demo / 部分材料。
- 材料严重不足(缺目标用户、缺成本、缺验收口径)时,先列出**信息缺口清单**并做"基于假设的评审"——把每个缺口当假设处理,不要中途停下来反复追问。
- 若 demo 是代码/仓库,先实际运行或阅读,不要只看用户描述。

### 第 1 步:逻辑审计
读 `references/logic-audit.md`,然后执行:
1. **假设提取与排序**:从计划文本提取隐含前提,按 重要性×不确定性 排出关键假设 TOP3–5。
2. **因果链检查**:问题→需求→方案→交付→采用→变现,逐跳问"凭什么成立",找出断点。
3. **可证伪性检查**:标出不可证伪的表述。
4. **Pre-mortem**:假设一年后项目死了,给出 TOP3 最可能死因及对应的早期预警信号。

### 第 2 步:落地与 demo 可验证性审计
读 `references/demo-verifiability.md`,然后执行:
1. **主张→实验映射**:每个核心主张对应一个最便宜的验证实验(指标、环境、样本量、pass/fail 阈值、成本)。
2. **Demo 有效性检查**:过拟合、游乐场条件、演示者偏倚、无基线对比等陷阱逐项排查。
3. **MVP 切分与验收标准**:给出量化的 pass/fail 口径,不允许"效果不错"这类表述。
4. **Kill criteria**:提前写死"出现什么信号就停止/转向"。

### 第 3 步:输出报告
用下面的模板。没有内容的节写"未提供材料,无法评估"并指明缺什么——**不要空节凑数,不要为凑结构编造内容**。

```markdown
# 可行性评审:<计划名称>

**结论:<GO / 有条件 GO / PIVOT / NO-GO>(置信度 n/10)**
一句话理由:<最关键的一条依据,直接说,不铺垫>

## 信息缺口
<材料缺失项逐条列出;它们已按假设纳入下文评审,不是待办提问。无实质缺口时省略本节>

## 关键假设 TOP N
| # | 假设(塌了项目死吗) | 当前证据/缺口 | 最便宜验证方式 | 预估成本与周期 |
|---|---|---|---|---|

## 逻辑审计
- **因果链断点**:<第几跳,断在哪,证据>
- **不可证伪表述**:<原文引用>
- **Pre-mortem TOP3**:<死因 → 预警信号>

## Demo 可验证性
- **Demo 主张**:<(demo 声称证明了什么)>
- **判定**:<可验证/不可验证 + 理由>
- **建议验收标准**:<量化 pass/fail>

## 红旗与亮点
- **红旗**:<问题,附证据>
- **亮点**:<优势,附证据>

## Kill criteria
1. 若 <实验/动作> 在 <期限> 内未达到 <阈值>,则 <停止 / 转向 / 降级为研究项目>。

## 下一步(按性价比排序)
1. <实验/动作>:<为什么排第一>
```

## 评分口径(默认不输出;仅当用户明确要求打分,或需要在多个计划之间做量化对比时使用)

五个维度各 1–5 分,每分必须挂证据;证据不足写"无法评分",禁止拍脑袋:
问题真实度 / 方案匹配度 / 技术可行性 / 资源匹配度 / 验证成本(反向,越低越高分)。
均分 ≥4 才支持 GO;<3 直接 NO-GO 或 PIVOT。

## 常见错误(自己避免)

- 复述计划书当分析。评审的增量是"计划书里没有的判断",不是摘要。
- 均匀用力。80% 的篇幅给关键假设和红旗,剩下的一笔带过。
- 只说不做。每份报告必须以"下一步"收尾——没有可执行验证动作的评审等于没评。
- 对 demo 只看演示不看条件。问自己:换一批数据、换一个环境还成立吗?
