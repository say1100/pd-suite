# 变更影响分析·分步指令

## C1 定位变更
1. 向用户确认三要素(材料里没有就问,这是本技能唯一允许主动追问的场景):**改什么(内容)/为什么改(动机)/改动生效在哪一层**(需求层→回 pd-requirements;方案层→回 pd-concept;实现层→pd-demo 局部更新)。
2. 判断变更类型:新增 / 修改 / 废弃 / 口径变更。

## C2 扫描关联
1. 列出工作区 `outputs/` 全部产物,对每份标注:
   - **直接命中**:产物正文引用了被变更的对象(需求 ID/功能名/指标名);
   - **间接波及**:依赖被变更对象的上游(如指标变更 → 依赖该指标的评测题全部受影响);
   - **无关**(附一句理由,防止"没看就标无关")。
2. 优先级:eval-plan/指标卡 > requirements(P0)> tradeoff > demo 产物。

## C3 影响分级
- 🔴 **需重做**:核心假设被推翻(如"自用改对外卖"→ 商业模式层全部重写);
- 🟡 **需重验**:局部修改后重跑对应评测(如新增指标 → 评测集补题、回归一次);
- 🟢 **无需动**:仅在范围外。

## C4 变更单
表:| 产物 | 影响(🔴🟡🟢) | 具体位置 | 建议动作 | 负责动作是谁(Agent/用户) |
末尾必须有两行:
- **回归范围**:需要重跑的评测/校验清单;
- **回流提示**:是否触发 pd-requirements / pd-eval 的更新。

## 模式 B|ADR 写法
文件名 `outputs/adr/ADR-00N-一句话标题.md`,正文:

```markdown
# ADR-00N:<标题>
- 日期 / 状态:已采纳
- 背景:<为什么当时要决策,引用变更单或对话>
- 决策:<一句话,可执行,无歧义>
- 理由:<2–3 条,每条可回溯到证据>
- 备选方案:<被否的选项 + 否决理由>
- 后果:<好处 + 代价 + 影响的产物清单>
```

写完提示用户:相关产物按变更单更新;若影响 P0 需求或指标卡,提示回 pd-eval 重验。
