# 需求梳理·分步指令

## S1 接料

1. 判断材料类型:访谈纪要 / 一句话想法 / 用户反馈列表 / 旧需求文档 / 混合。
2. 列**信息缺口清单**(目标用户?核心场景?付费方?验收口径?),放在产物开头;缺口按假设处理并在条目后标 `[假设]`,**不中途追问**。
3. 材料是代码/仓库时先浏览再提需求,不要只看用户的转述。

## S2 结构化

1. 逐段提取三元组:**谁(具体角色,禁止"用户"二字了事)——在什么场景——痛什么**。
2. 一条需求 = 一个可独立验证的痛点,不把多个痛点合并成一行。
3. 隐含前提显式化:"用户自然会来"这类断言 → 拆成待验证假设,不冒充需求。
4. 写入 schema 表;每条带来源(纪要第 x 段 / 反馈第 x 条),保证可回溯。

## S3 优先级

1. MoSCoW 精神落到三档:P0(没有它产品不成立)/ P1(明显增值但可延后)/ P2(观察)。
2. 每条优先级必须有一句**依据**(引用痛点强度/出现频次/是否阻塞其他需求);写不出依据的默认 P1 并标注 `⚠依据待补`。
3. 冲突与依赖:行内 `⚠冲突` / `⚠依赖:REQ-00x`。
4. KANO 判断只在用户要求时做(见 references/methods.md)。

## S4 校验交付

1. 运行 `python skills/pd-requirements/scripts/check_schema.py outputs/requirements.md`(cwd=工作区根;单独拷包时 `python scripts/…`)。
2. exit 0 → 交付;非 0 → 按 `REQ_SCHEMA_JSON:` 的 errors 修复后重跑,**带病不交付**。
3. 交付语固定三句:需求条数与 P0 数 / 最大信息缺口 / 下一步建议(pd-concept)。
