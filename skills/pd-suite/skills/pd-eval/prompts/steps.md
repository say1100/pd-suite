# 验证评估·分步指令

## E1 验证链路
1. 从 requirements 的 P0 与用户访谈提炼**产品主张**,两条来源:需求侧("目标用户需要 X 且愿意 Y")与技术侧("方案能做到 X")。
2. 每条主张填五行链:主张 → 主指标 → 数据源(track-events 事件 / 数据集) → 实验设计 → 结论口径。
3. 缺任何一行 → 该主张标注 `⛔当前不可验证`,并写清缺什么;**不许删主张,也不许编数据源**。

## E2 指标卡
1. 一指标一卡,字段:| 指标 | 定义 | 公式 | 数据来源 | 基线 | 阈值(pass/fail) |
2. 基线未知时写"首测建立",但阈值仍须先写死——阈值不是看到数据后再定的。
3. 区分北极星(1 个)+ 护栏指标(防副作用,如北极星涨但留存跌即为失败)。
4. 模糊词黑名单:效果/不错/显著/明显/大幅/大幅提升——脚本会拦。

## E3 数据侧设计
1. **埋点复核**:对照 track-events.md,逐条主张确认其数据源事件真的存在且字段够用;缺 → 列"补埋点清单"退回 demo,不许跳过。
2. **数据集构建**(涉模型/算法时):来源、目标规模(给最小统计意义的量,如每类 ≥30)、标注规范**必须含 2 个已标注样例**、划分(训练/留出,留出集永不参与调参)。
3. **基线先立**:与什么比?(现有方案/人工/竞品/随机)没有基线的指标没有意义。

## E4 实验与 kill criteria
1. 每实验一卡:测什么/在哪测/样本量/pass·fail 数值/成本与周期。写法范例:"10 名目标用户独立完成核心任务且 SUS≥70;不达标即停"。
2. kill criteria 至少 3 条,其中**至少 1 条需求侧**(如"2 个月内无 ≥3 位目标用户愿完成核心任务 → 需求侧判死,停止投入")。
3. kill criteria 要提前经用户确认,事后改 = 无效。

## E5 结论回填(eval-report.md)
1. 模板:结论(引用指标卡编号)→ 数据摘要 → 偏差与异常 → 下一步(迭代/停止/转向)。
2. 结论只允许三种:PASS / FAIL / 数据不足(附需要多少数据才够)。
3. FAIL 时不许润色成部分成功;按 kill criteria 走,并回流:需求变更进 requirements,方案变更进 concept。
